# 막힌 문제 진단

규칙을 하나 더 얹기 전에 "왜 깨지는가"를 샘플 여러 개로 확인하고, 뒤 단계가 그대로 쓸 수 있는 수정안과 검증 샘플을 남긴다.

## 절차

1. **재현을 특정한다.** 어느 PDF, 어느 쪽, 어느 수식 번호 또는 박스인지. 사용자에게 경로·쪽을 받아 기록한다(PDF 자체는 커밋하지 않는다).
2. **격리한다.** 어느 함수·정규식·임계값이 결과를 결정하는지 코드에서 찾는다. `-v` 로그나 변환 결과 전체를 메인 세션에 올리지 않는다. `verify-run` 에이전트에게 돌리게 하고 해당 수식 줄만 받는다.
3. **패턴을 잡는다.** 깨지는 샘플 2개 이상과 멀쩡한 샘플 1개 이상을 대조한다. 샘플 하나만 보고 규칙을 더하면 다음 논문에서 또 깨진다.
4. **기준에 비춘다.** `docs/decisions/`에 관련 판정 기준이 있으면 그것으로 "규칙 버그"인지 "기준이 없는 영역"인지 가른다. 후자면 `decide-direction`으로 넘기고 멈춘다.
5. **수정안을 2개 이상 세운다.** 각각 영향 범위(어느 PDF 유형의 결과가 바뀌나)와 회귀 위험. 하나를 고르고 이유를 적는다.
6. **기록한다.** `docs/issues/<slug>.md`, 틀은 `docs/issues/_template.md`. **검증 샘플** 절은 `verify-run`이 그대로 돌릴 수 있게 경로 · 쪽 · 식 번호 · 기대 결과 형식으로 적는다.

## 산출물

- `docs/issues/<slug>.md` 한 장.
- 메인 세션에는 원인 1줄, 고른 수정안 3줄, 파일 경로.

## 하지 않는 것

- 코드 수정(그건 `implement-rule`).
- 원인을 못 찾은 채 규칙 추가를 제안하기. 못 찾았으면 "못 찾음"과 다음에 볼 샘플을 적는다.
